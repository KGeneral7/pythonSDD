# 專案發布流程

這個技能只適用於目前專案的完整發布收尾。它的輸入前提是使用者已完成實際人工測試，並明確表示沒有問題；流程完成後，程式、文件、PR、發布版本與分支生命週期都必須有可驗證的結果。

## 啟動條件與權限

- 若使用者沒有明確表示「人工測試完畢且沒有問題」，先停止在本地檢查前並請使用者確認；不要把自動化測試當成人工測試的替代品。
- 只有在使用者要求完整發布，或明確授權提交 PR、發布、合併及刪除分支時，才執行遠端寫入與分支刪除。只要求 code review 時，完成審查與必要修正後停在本地。
- 發布與合併是外部副作用；若使用瀏覽器或其他介面在送出按鈕前需要即時確認，遵守該介面的確認要求。
- 這是區域技能，只修改目前專案中的檔案與其 GitHub／Git 遠端；不要寫入全域技能目錄，也不要替其他專案改設定。

## 1. 發布前盤點

先做唯讀檢查，確定發布範圍與基準：

- 讀取 `git status --short --branch`、`git branch -vv`、遠端 URL、目前 commit 與預設主分支；不要自行猜測分支名稱。
- 找出目前功能分支、基準分支、遠端 head SHA，以及是否已有相同 base/head 的 PR、tag 或 release。
- 分開檢查「已提交功能差異」與「工作區未提交差異」。未追蹤檔案、其他功能的修改及使用者正在進行的工作都必須保留，不得使用 `git add -A`、`git clean`、`git reset --hard` 或 `git checkout --` 覆蓋它們。
- 若目前分支不是要發布的功能分支、工作區有不明來源的修改，或無法判定哪些檔案屬於本次發布，先說明範圍並停止遠端操作。
- 若專案有 `.specify/memory/constitution.md`，讀取其中的分支、PR、驗證與清理要求，並把它們視為本流程的門檻。

## 2. 本地 code review 與必要修正

- 以基準分支比較完整差異，逐一檢視程式、測試、設定與文件；同時檢查工作區差異是否應納入發布。
- 針對正確性、回歸風險、錯誤處理、資料／狀態生命週期、效能與測試覆蓋評估問題。
- 只有確認會影響需求、規格、穩定性或發布安全的問題才直接修正；修正應限制在本次範圍，使用 `apply_patch`，不要順手重構無關程式。
- 每個修正都要先補或調整適切的回歸測試，再執行針對性測試；必要時重新檢視 diff。若問題不需要修正，記錄判斷依據，不要為了讓流程變綠而改測試。

## 3. 文件與 SDD 同步

- 使用 `rg --files` 盤點規格、計畫、任務、快速驗證、變更紀錄、版本資訊與發布設定；確認文件中的功能狀態、分支名稱、PR、tag、測試結果與實際程式一致。
- 對 Spec Kit 專案，至少檢查 `spec.md`、`plan.md`、`tasks.md`、`quickstart.md`、`research.md`、`data-model.md`、checklist 與憲章。只在有實際證據時勾選任務或宣告完成。
- 先依 `speckit-analyze` 的唯讀規範執行跨文件分析；若發現矛盾、過時狀態、缺漏或憲章違反，修正最相關的文件或程式後重新分析，直到沒有可處理問題，或把真正的外部阻塞記錄清楚。
- PR body 必須連結對應 `specs/<feature-id>/` 文件，並包含人工測試已完成、自動化驗證、已知限制及發布資訊。

## 4. 驗證與提交

- 依專案既有命令執行完整自動化測試、編譯／型別／lint 檢查、`git diff --check`、入口 smoke test 與必要的效能回歸；不要只執行單一測試就宣告發布。
- 整理測試結果與人工測試前提。若驗證失敗，先修正或停止，不得帶著失敗結果進入合併。
- 只 stage 已確認屬於本次發布的明確路徑；檢查 staged diff 後再建立清楚的 commit。不要納入 `day3/` 或其他使用者檔案，除非使用者明確要求。
- 推送到已確認的功能分支時使用一般 push；不要 force push。推送後重新取得實際 head SHA。

## 5. 建立或更新 PR

- 先搜尋相同 base/head 的既有 PR；有既有 PR 就更新並驗證，不要建立重複 PR。PR 應使用精確的基準分支與功能分支。
- PR 標題、摘要、文件連結、測試結果、人工驗收結果、風險與發布版本要與現況一致。使用者明確要求合併時建立可合併的非 draft PR；未授權合併時保留 draft 或停在審查階段。
- 確認 PR 的 `mergeable` 狀態、衝突、必要檢查與最新 head SHA。若 GitHub 沒有 Actions 或狀態檢查，明確記錄「無自動化檢查，採本地驗證」。
- 合併前使用 expected head SHA，避免在 PR 被更新後誤合併未審查的內容；多個提交通常使用 squash merge，除非專案規範指定其他方式。

## 6. 合併後發布

- 先確認 PR 在遠端確實是 `merged`，取得實際的主分支合併提交 SHA；不要把功能分支 SHA 當成 squash merge 後的版本 SHA。
- 從專案既有版本來源決定版本號。若 tag 或 release 已存在，先確認是否指向同一個合併提交；指向不同提交時停止並回報，不要覆寫或強推。
- 依專案既有機制建立並推送 annotated tag，然後建立正式 release 與發布說明；若沒有既有發布自動化，至少發布與合併提交一致的 tag，並在結果中明確說明實際完成的層級。
- Release notes 應摘要本次功能、重要修正、驗證結果、PR 連結與已知限制；不要捏造未執行的測試或資產。

## 7. 憲章要求的分支清理

分支清理是發布完成的一部分，但必須以安全順序執行：

1. 只有遠端確認 PR 已合併後，才可清理功能分支；PR 僅關閉或仍開啟時必須保留。
2. 先檢查工作區沒有未提交或未追蹤的使用者工作、功能分支沒有未推送 commit，且目前已切換到主分支或其他安全位置。
3. 刪除遠端功能分支，再以一般合併保護的 `git branch -d <feature-branch>` 刪除本地分支；不得用 `-D` 取代合併檢查。
4. 重新驗證遠端 branch、local branch、目前 HEAD、主分支同步狀態與工作區狀態。
5. 若本地分支正被使用、工作區有未提交／未追蹤變更，或權限／工具阻止刪除，不得冒險切換或丟棄變更；保留分支，並在文件或發布報告中記錄原因、保全方式與後續清理動作。不能宣稱分支生命週期已完成。

本專案憲章的關鍵依據是 `.specify/memory/constitution.md`：合併後才可刪除遠端與本地功能分支，且 PR 審查必須檢查清理結果；若無法清理，必須記錄原因與處理方式。

## 完成報告

報告至少包含：

- code review 發現與實際修正（或判定不需修正的理由）。
- 文件更新範圍與 SDD 分析結果。
- 測試／編譯／smoke／效能結果，以及人工測試已由使用者確認。
- commit、功能分支、PR URL、合併提交、tag／release URL。
- 遠端與本地分支清理結果；若未清理，必須逐項列出原因與後續處理方式。
- 保留的使用者未提交檔案，確認它們沒有被提交、刪除或覆蓋。

## 專案預設位置

本專案通常使用 `pvpve_escape/` 作為程式目錄、`pvpve_escape/tests/` 作為測試目錄、`specs/` 作為 SDD 文件目錄；這些只是預設，仍須以發布前盤點的實際結構為準。
