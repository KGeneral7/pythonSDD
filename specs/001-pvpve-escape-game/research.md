# 研究與設計決策：PvPvE 中央撤離競技遊戲

## 研究範圍

本階段針對規格中的技術未知、執行環境依賴、互動遊戲架構、計時方式與驗證策略進行決策。專案目前是 Python 學習型桌面遊戲專案，既有程式使用 Pygame，但虛擬環境尚未安裝 Pygame。

## 決策 1：執行環境與依賴

- **決策**：使用 Python 3.11.5；將 Pygame 安裝在專案 `.venv`；測試使用 Python 標準函式庫 `unittest`。
- **理由**：符合專案憲章與目前環境，能延續既有 Pygame 練習，不需要引入伺服器、資料庫或大型遊戲引擎。`unittest` 不增加額外測試依賴，適合目前的學習型專案。
- **替代方案**：使用全域 Pygame、使用第三方測試框架、改用其他遊戲框架。
- **不採用原因**：全域安裝違反憲章；第三方測試框架與其他框架會增加安裝與學習範圍，且不直接支援本次需求。

## 決策 2：程式結構

- **決策**：建立獨立的 `pvpve_escape/` Python 套件，依責任拆成設定、資料模型、純規則、控制器、角色、世界更新、繪製與入口模組。
- **理由**：本功能同時包含六種角色、玩家生命週期、怪物重生、計時、撤離與開發者測試；若全部放在一個檔案，將難以逐步驗證。模組邊界仍維持簡單函式、資料類別與少量明確類別，不建立 ECS 或大型框架。
- **替代方案**：將整個遊戲放在一個 `main.py`、或引入第三方遊戲架構。
- **不採用原因**：單檔會讓輸入、更新、繪製與規則互相耦合；大型架構超過目前學習目標。

## 決策 3：輸入、更新與未來多人替換點

- **決策**：以 `InputState` 作為每幀輸入資料，將人類玩家控制、無 AI 假玩家控制與未來網路輸入視為不同控制來源；本次只實作人類控制與固定假玩家。
- **理由**：可以維持本次單機範圍，又不把 `PlayerState` 綁死在鍵盤事件。未來將假玩家替換成網路玩家時，主要替換控制來源，不需改寫生命、傷害、撤離等規則。
- **替代方案**：直接在玩家類別內讀取鍵盤、現在就建立網路同步層。
- **不採用原因**：直接讀取鍵盤會降低測試性；網路同步不是本次範圍，會增加伺服器權威、延遲與斷線處理。

## 決策 4：世界座標與鏡頭

- **決策**：使用 2400×1400 的世界座標與 1280×720 的視窗；鏡頭以人類玩家為中心並限制在世界邊界內，所有物件先以世界座標更新，再轉為畫面座標繪製。
- **理由**：符合大地圖跟隨鏡頭的需求，且能用清楚的座標轉換驗證地圖邊界、出生區與中央撤離區。
- **替代方案**：整張地圖固定顯示在視窗內、或使用可縮放地圖。
- **不採用原因**：固定小地圖無法提供規格要求的大地圖移動感；縮放會增加座標轉換與視覺驗證成本。

## 決策 5：計時與更新順序

- **決策**：所有遊戲時間以秒為單位的浮點數保存；每幀由時鐘取得經過時間並限制單幀最大更新時間為 0.05 秒。更新順序固定為輸入、計時與冷卻、移動碰撞、攻擊與傷害、死亡與重生、撤離與勝負、繪製。
- **理由**：限制單幀時間可避免視窗卡頓時物件瞬間穿越邊界；固定順序可讓撤離勝負、最後一擊與同幀裁決結果可重現。
- **替代方案**：所有物件使用固定每幀像素移動、或讓不同系統自行決定更新順序。
- **不採用原因**：固定像素速度會受實際 FPS 影響；不固定順序會造成難以重現的勝負與傷害結果。

## 決策 6：戰鬥數值與資料驅動方式

- **決策**：將比賽時間、地圖尺寸、玩家基礎數值、怪物數值、彈匣與補彈、角色攻擊、被動、大招與配件數值集中在 `config.py` 或角色設定資料中；規則函式只接收資料與時間，不直接散落常數。
- **理由**：規格要求未指定的數值要有明確首版初值並可調整，也符合憲章中設定值集中與公式可追蹤的要求。
- **替代方案**：將數值寫在各個更新函式內、或建立外部資料庫／編輯器。
- **不採用原因**：散落常數不利於學習與平衡；外部資料系統超出單機原型範圍。

## 決策 7：測試策略

- **決策**：使用 `unittest` 測試不依賴畫面的純規則，包括強化公式、能量、彈藥、最後一擊、死亡重置、重生、配件冷卻與撤離；使用快速開始文件記錄可重複的視窗手動測試。
- **理由**：既有專案沒有測試架構，先以標準函式庫建立低門檻測試，再以手動情境驗證 Pygame 畫面與輸入。
- **替代方案**：只依賴手動測試、或先建立完整整合測試框架。
- **不採用原因**：只手動測試無法穩定驗證邊界公式；完整整合框架會延後第一個可玩的版本。

## 決策 8：外部介面與契約

- **決策**：本次不建立 `contracts/`。遊戲是本機內部桌面應用，沒有對外 API、資料庫、伺服器或檔案交換格式。
- **理由**：規格明確將線上多人與外部服務排除在本次範圍外。
- **替代方案**：現在先建立網路封包或多人同步契約。
- **不採用原因**：會把未來功能誤納入本次實作，且沒有可驗證的外部消費者。

## 研究結論

所有計畫層技術未知均已決定，沒有需要保留的 `NEEDS CLARIFICATION`。下一階段建立資料模型、快速開始驗證指南與完整實作計畫。
