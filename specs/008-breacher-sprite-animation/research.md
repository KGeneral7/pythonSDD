# Phase 0 研究：破陣者 Q 版像素角色與八方向動畫

## 研究範圍

本研究確認目前角色繪製、世界更新、戰鬥動作、素材載入與測試的接點，並為規格中的素材格式、方向判定、動畫狀態、攻擊觸發與錯誤回退做出決策。

## 現況盤點

- `pvpve_escape/rendering.py` 已有地圖素材的模組相對路徑載入、尺寸檢查、`convert_alpha()` 與模組級快取；角色與怪物目前仍由 `pygame.draw` 幾何圖形繪製。
- `draw_selection()`、`_draw_player_roster()` 與 `draw_world()` 都會直接呼叫角色幾何繪製函式，因此需要一個共用的「圖片優先、幾何 fallback」入口。
- `pvpve_escape/world.py` 的 `update_world()` 依序處理玩家生命週期、玩家輸入與動作、效果、怪物、彈藥、撤離與鏡頭；`_apply_action()` 是普攻、戰術與終極動作的共同套用點。
- `PlayerState.last_attack_time` 目前服務生命恢復延遲，不能拿來表示攻擊動畫進度；模型需要追加獨立且有預設值的動畫狀態。
- `pvpve_escape/assets/` 目前只有地圖圖片，沒有角色或怪物圖片；`requirements.txt` 只有 Pygame，不需要為本功能新增套件。
- 測試採 `unittest`，並已有 headless Pygame、繪製快取清除與完整回歸測試支援。

## 決策 1：使用單張圖片並建立角色專用資產目錄

**決策**：使用 8 張待機圖、32 張移動圖與 32 張攻擊圖，共 72 張獨立 PNG，放在 `pvpve_escape/assets/characters/breacher/`，依 `idle`、`move`、`attack` 與方向分層；所有來源畫布固定為 1024×1024。

**理由**：使用者要求每個方向與每個動作各自提供四張圖；單張檔案能讓單一幀獨立驗證與 fallback，也符合目前地圖素材的檔案式管理方式。

**替代方案**：使用一張大型 sprite sheet。這會減少檔案數，但增加裁切座標、單幀錯誤隔離與測試複雜度，且不符合目前的交付形式，因此不採用。

## 決策 2：以瞄準方向作為角色面向

**決策**：將有效的 `aim_direction` 量化成八個 45 度區段，固定索引為右、右下、下、左下、左、左上、上、右上；零向量沿用上一個有效方向，初始值為右。

**理由**：目前對局角色已以 `aim_direction` 代表面向，且武器與技能都依瞄準方向運作。使用預先繪製的八方向圖片可避免執行期旋轉造成像素模糊或槍盾翻轉。

**替代方案**：以移動方向作為面向，或只保留四個軸向。前者會讓玩家向前移動但瞄準側面時角色朝向錯誤；後者無法滿足八方向需求，因此不採用。

## 決策 3：在玩家狀態保存動畫進度

**決策**：新增 `PlayerAnimationState`，保存 `facing_direction_index`、移動狀態、移動經過時間、攻擊經過時間與 `attack_hold`；由世界更新階段推進，死亡／重生時清除。

**理由**：動畫進度是跨繪製幀的遊戲狀態，放在玩家資料可以讓 headless 測試直接驗證，也能讓選角、對局與玩家列表共用一致資料。獨立欄位可避免誤用生命恢復用的 `last_attack_time`。

**替代方案**：由 renderer 以全域快取保存每個玩家動畫，或從 `primary_cooldown` 推導攻擊幀。全域快取會增加玩家生命週期與測試清理問題；冷卻時間不等於視覺動作時間，且無法涵蓋所有技能，因此不採用。

## 決策 4：從共同動作套用點觸發攻擊動畫

**決策**：所有成功套用的普攻、戰術技能與終極技能在 `_apply_action()` 觸發同一套四格攻擊動畫；連續型技能只延長攻擊狀態，不重設已播放幀。

**理由**：`_apply_action()` 已是各角色動作進入世界效果的共同邊界，可以避免在多個輸入分支重複觸發。使用者已指定普攻與技能共用攻擊圖片，四格動作不再為每個技能建立額外素材。

**替代方案**：在每個角色輸入分支個別觸發，或只依玩家是否按住普攻觸發。前者容易遺漏技能與測試路徑，後者無法反映由世界接受的技能動作，因此不採用。

## 決策 5：固定動畫速度與優先順序

**決策**：移動幀每 `0.10` 秒切換並循環；攻擊幀每 `0.06` 秒切換，四格總長 `0.24` 秒；攻擊期間遮蔽移動動畫，完成後依當下移動狀態恢復。

**理由**：10 FPS 的移動循環足以呈現 Q 版步伐，較快的攻擊循環能讓技能回饋明確；固定時間也能以 `delta_time` 做可重複測試，並受現有最大時間步長保護。

**替代方案**：依畫面更新次數切幀，或讓每種技能各自決定速度。依更新次數會受到 FPS 影響，技能個別速度則超出本 MVP 並增加素材與狀態規則，因此不採用。

## 決策 6：素材驗證失敗時回到幾何圖形

**決策**：載入器驗證圖片存在、可讀取、尺寸為 1024×1024、四角為透明像素且含透明背景；單張失敗時回傳不可用結果，由繪製入口使用既有幾何角色。每個資產鍵只記錄一次並發出一次診斷警告，避免每幀重複處理。

**理由**：圖片是可替換資產，不能讓單張檔案阻斷遊戲；使用者已選定幾何 fallback。候選生成圖片的預覽曾呈現棋盤格外觀，因此必須確認棋盤格不是烘焙背景。

**替代方案**：啟動時要求所有圖片完整，或顯示空白角色。啟動阻擋降低遊戲可用性，空白角色會損害辨識與測試，因此不採用。

## 決策 7：顯示尺寸與圖片處理

**決策**：來源圖片維持相同的 `1024×1024` 畫布與透明錨點；對局角色逐張擷取實際非透明角色區域，再以最近鄰方式直接重採樣並置中於 `50×50` 顯示畫布，選角與玩家列表使用各自較小的 UI 尺寸。執行期不旋轉、翻轉或重新拼接槍盾。

**理由**：來源固定畫布可提供一致的檔案驗證基準；逐張取出實際非透明區域並使用固定 `50×50` 顯示格，可消除生成時透明留白與角色外框比例差異造成的大小跳動；最近鄰縮放能保留像素邊緣；不做旋轉或翻轉可維持使用者要求的俯視角、分離槍盾與手部連接。

**替代方案**：以向量幾何重畫武器會破壞素材原本的槍盾設計，因此不採用。只依來源 PNG 的透明邊界裁切可能改變顯示錨點，因此正式圖片仍維持完整 `1024×1024` 畫布；執行期快取每張圖的實際非透明區域與 `50×50` 結果，進入新對局前清除快取並重新讀取。對於生成器背景、透明 alpha 或畫布／置中等格式問題，可做不改角色內容的確定性整理；創意內容問題仍必須重新生成。
