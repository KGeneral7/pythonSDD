# 研究與技術決策：小怪動態尋路與營地遊蕩

## 研究範圍

本研究只針對目前 `pvpve_escape` 內部的怪物更新、地形幾何與固定地圖，不引入外部導航服務或新套件。研究結果要回答六個問題：小怪為什麼會卡牆、怎麼在目前牆體變化後使路徑失效、怎麼讓小怪在沒有目標時遊蕩、怎麼不破壞三種怪物原本的戰鬥差異、怎麼套用新的速度比例，以及怎麼避免玩家 0 號開場貼近生怪區。

## 現有程式觀察

1. `pvpve_escape/world.py` 的 `update_monsters` 目前每幀選擇全體存活玩家中距離最近者，直接使用目標方向移動；沒有偵測距離、牆體視線、路徑節點或營地行為。
2. `pvpve_escape/terrain.py` 的 `move_circle_with_obstacles` 已能處理圓形物件與牆體的基本碰撞，並保留 `first_obstacle_on_segment`、`snapshot_obstacles` 等可重用幾何功能；但它的責任是阻止一次位移，不是替 AI 找到繞牆路線。當小怪每幀重試同一個被阻擋的方向時，會停在同一接觸點。
3. `snapshot_obstacles` 只回傳 `solid` 牆體的 ID、種類與矩形。`ObstacleState.solid` 會在薄牆被設為 `destroyed=True` 後變成 `False`，所以現有快照天然能表達「薄牆消失、厚牆仍在」。
4. `update_world` 的順序是玩家動作、效果、`update_monsters`、怪物投射物；既有玩家破牆動作在怪物更新前完成，因此小怪可以在同一更新週期讀取破牆後的 `match.obstacles`。
5. 地圖為 2400x1400，現有固定營地為四個，每個營地生成 `CHASER`、`SHOOTER`、`BRUTE` 各一隻；因此最多同時更新 12 隻小怪，適合以小型固定網格做可預期的即時搜尋。
6. `pvpve_escape/rendering.py` 目前以營地中心繪製半徑 64px 的「怪物區」標記；這個既有視覺範圍可作為返營完成判定的明確基準，並與 700px 的遊蕩範圍分開。
7. `create_monsters()` 以四個營地中心加上固定偏移建立實際怪物出生點；玩家 0 號使用 `config.SPAWN_POINTS[0]`，因此出生距離可在建立 `MatchState` 後同時對營地中心與實際怪物座標驗證。

## 決策 R-001：採用固定 40px 網格的八方向 A*

**決定**：新增 `navigation.py`，以 40px 格寬把世界轉為約 60x35 的網格，使用八方向 A*；每個格子的障礙判斷使用與既有移動碰撞一致的「牆矩形向外膨脹小怪半徑加 4px」安全區。禁止兩個正交鄰格被阻擋時的斜向移動，避免切過牆角；精確線段掃掠只保留在實際起點／第一節點、起點中心備援與精確安全目標的必要段落，實際移動再交給既有碰撞函式。

**理由**：目前地圖固定、牆體是軸對齊矩形，網格能用少量可讀的 Python 函式處理不同怪物半徑，並讓路徑是否可行容易以單元測試重現。40px 在 2400x1400 世界中只產生 2100 格，對 12 隻小怪足夠輕量；4px 安全距離與 no-corner-cut 則避免「格中心安全但圖形切過牆角」的視覺與碰撞問題。若每個 A* 鄰接都掃描全部牆體，牆角多怪同時重算會造成遊戲整體卡頓，因此不採用逐邊完整掃掠。

**替代方案**：

- **只用牆邊滑動／wall following**：不需網格，但在多面牆、目標移動與厚薄牆混合時容易產生迴圈，難以保證可達目標。
- **牆角可見圖**：節點數可能較少，但需處理圓形半徑、牆角偏移、邊界與動態破牆後重建節點，對目前學習型專案的可讀性與測試成本較高。
- **每幀暴力嘗試多個方向**：可暫時避開單一牆，但沒有穩定的全局路線，仍可能在複雜障礙前反覆抖動。

## 決策 R-002：以即時固體牆快照使路徑失效

**決定**：`update_monsters` 每次更新取得一份 `snapshot_obstacles(match.obstacles)`，每隻小怪保存上次使用的簽章。簽章不同時，不等待 0.25 秒計時器，立即清除路徑並依當前障礙重新搜尋。

**理由**：使用中的 `match.obstacles` 是唯一反映玩家破牆後狀態的來源；讀取 `config.OBSTACLE_LAYOUT` 會把已破壞薄牆錯誤地復原。`update_world` 目前又先處理玩家動作，所以「下一次遊戲更新」可以落在破牆同一幀後的小怪更新中。簽章包含 ID、種類和矩形，能捕捉牆體存在與幾何改變。

**替代方案**：

- **只按固定時間重算**：破牆後可能保留最多一個間隔的舊路徑，不符合即時改道要求。
- **只在每隻怪物移動到節點時重算**：小怪可能先沿已不存在的繞路走很久。
- **重新建立整份固定地圖**：無法正確表達一場比賽中已被破壞的薄牆。

## 決策 R-003：用三狀態管理目標生命週期

**決定**：在 `models.py` 新增 `MonsterBehavior.WANDER`、`CHASE`、`RETURN`。未鎖定目標時只對距離 `<= 520` 且直線未被固體牆阻擋的存活玩家做目標選擇；追擊中的既有目標在死亡或距離嚴格大於 520px 時解除，之後返營。

**理由**：把目標選擇和移動目的地分開，可以同時保留「已看到玩家但玩家繞到牆後仍能繞牆追擊」與「牆後玩家不會被新發現」兩項要求。`RETURN` 也能保證沒有目標時不會從全圖任意位置直接開始遊蕩，且攻擊判斷可以明確限制在 `CHASE`。

**替代方案**：

- **只有布林值 `has_target`**：無法區分返營和已在營地的遊蕩，容易在返營途中產生遊蕩點或攻擊。
- **每幀重新選最近玩家**：玩家走到牆後或死亡時會立刻換目標，且怪物不會保留合理的追擊生命週期。
- **加入額外的目標距離遲滯區**：可減少邊界抖動，但會改變規格明定的 520px 解除條件；本版先採明確 `<=`／`>` 規則並以單次更新狀態轉換和邊界測試控制抖動。

## 決策 R-004：以可重現候選點實作營地遊蕩

**決定**：營地中心取自 `config.MONSTER_CAMP_POINTS[spawn_zone_id]`；候選點限制在 700px 圓形範圍、世界安全邊界及目前牆體之外。返營距離營地中心 `<= MONSTER_CAMP_ARRIVAL_RADIUS`（64px）即算完成，這與遊蕩範圍分開。以 `monster_id` 和 `wander_index` 建立固定的角度／半徑序列，不保存全域亂數狀態；抵達後以 `MONSTER_WANDER_PAUSE=0.75` 秒累計停留，允許一個 `delta_time` 的更新誤差，再選下一點。遊蕩移動使用該怪物目前速度的 50%。

**理由**：功能需要「遊蕩」而非不可預測的隨機噪音。可重現序列讓自動化測試能確認每種怪物完成至少兩個不同安全點，也避免多隻小怪因共享隨機狀態而難以重現。使用既有 64px 營地標記作為返營完成範圍，可避免把遊蕩半徑誤當作返營判定。候選點失敗時可繼續嘗試，全部失敗則安全停留並稍後重試。

**替代方案**：

- **使用全域 `random`**：測試會受其他遊戲行為的隨機呼叫影響，難以重現卡牆案例。
- **營地內固定一個點**：不符合多個遊蕩點的可觀察行為，也容易讓多隻怪物重疊。
- **允許任意全圖漫遊**：破壞營地警戒語意，並提高不必要的尋路與越界風險。

## 決策 R-005：導航只改變到達方式，不改寫戰鬥定位

**決定**：保留 `MonsterDefinition` 的半徑、攻擊種類、攻擊距離、偏好距離與投射物欄位；移速仍集中在 `config.py`，但依最新平衡設定，追獵獸為玩家基礎移速 90%，砲台蟲與重裝巨獸各自原始速度套用相同相對增幅。導航只提供下一個安全移動方向；接觸傷害與 `SHOOTER` 的攻擊邏輯仍放在追擊狀態的既有分支。

**理由**：三種怪物的差異已由 `monsters.py` 定義，路徑問題不需要重新設計戰鬥。把攻擊限制在 `CHASE` 可直接滿足遊蕩／返營不得攻擊，又能避免重構造成回歸。

速度調整只改變移動平衡，不把三類怪物設成相同絕對速度，因此仍保留追獵獸、砲台蟲與重裝巨獸的相對定位；玩家 0 號出生點則以與所有營地及實際怪物出生點至少 200px 的自動化斷言保護。

## 決策 R-006：不引入新套件，採小型可測試介面

**決定**：導航模組只依賴專案模型、地形純函式和 Python 標準函式庫；不使用 `pygame` 顯示 API、不使用網路、不建立背景執行緒。所有會影響位置的計算保留在 `world.py` 的固定更新階段。

**理由**：遊戲已有完整幾何資料結構與 `unittest` 基礎；純 Python 導航可以在無視窗測試，符合憲章的可理解、小步驟和不過早引入大型抽象要求。

## 未採用外部研究的說明

本功能的選擇取決於本專案既有地圖尺寸、資料類別和碰撞函式，沒有需要查詢會隨時間變化的外部規格或服務。A*、矩形膨脹與線段碰撞的具體使用方式已在本文件以目前程式結構和可測試的決策固定下來。

## 決策 R-007：砲台蟲偏好位置不可達時先繞行

**問題**：砲台蟲以目標反方向 300px 的位置作為導航終點；該位置可能落在未摧毀牆體內，或雖然是安全點卻被牆封在目前不可達區域。若直接把最近安全格當作終點，怪物抵達牆角／封閉區邊緣後會清空路徑，下一次重算仍得到同一格，因此會長時間停在牆前。另一種情況是實際碰撞允許的位置位於導航額外 4px clearance 內，重算時首段被錯誤判定為從牆內開始，造成相同卡住結果。

**決定**：`world.py` 先以目前固體牆和 `radius + MONSTER_NAVIGATION_CLEARANCE` 驗證砲台蟲的偏好位置；若偏好位置不安全，或偏好位置安全但 `_refresh_monster_path` 找不到路徑，暫時以目標位置作導航終點，讓既有 A* 找到繞牆／離開封閉區的路線，之後每次路徑重算再恢復偏好距離判定。`navigation.py` 的首段若只從規劃 clearance 內向外離開，改以既有實體半徑 `first_obstacle_on_segment` 再驗證，允許合法離開但仍拒絕真正穿牆。

**理由**：不新增狀態欄位、不改變砲台蟲 420px 攻擊範圍、300px 偏好距離或投射物規則，就能處理牆內偏好點、偏好點位於封閉區，以及由多格牆組成的牆角；實際位置仍由 `move_circle_with_obstacles` 保護。三個回歸測試分別固定這三種卡住原因。

## 修正後確認（2026-08-28）

- 砲台蟲厚牆內偏好位置、長牆轉角 clearance，以及安全偏好點被厚牆封閉的三個回歸情境均通過。
- 聚焦導航／怪物／地形測試共 74 項通過；完整測試共 229 項通過。
- 固定地圖效能量測為 120 幀暖機、600 幀、約 8.438 秒、71.11 FPS；沒有新增套件或每幀圖片讀取。
